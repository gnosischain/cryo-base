# AGENTS.md — cryo-base

Build-only repository: one Dockerfile that compiles a pinned commit of Paradigm's `cryo` with two source patches and publishes it as `ghcr.io/gnosischain/cryo-base`. Nothing here runs in production and nothing here knows a warehouse.
Production data flow: chain archive RPC → `cryo` binary (this image, spawned as a subprocess by the `gc-cryo-indexer` app whose image is built `FROM` a **date tag** of this one) → parquet in the pod's scratch dir → ClickHouse `execution`, `execution_live`, `celo_execution`.
The one rule: every table the indexer writes inherits this binary's output shape, and a wrong patch is silent until rows have landed. Prove a patch on a one-block local extraction before the indexer re-pins its base; a green build here proves nothing (see below).

## Where this runs (production)

This image is never deployed. Its binary runs inside `ghcr.io/gnosischain/gc-cryo-indexer` (indexer `Dockerfile:2` pins `FROM ghcr.io/gnosischain/cryo-base:20251201`, not `latest`), which the private deployments repository runs on GKE Autopilot with **no `command`/`args`**, so every workload goes through the indexer's shell entrypoint. That entrypoint echoes `OPERATION` (indexer `scripts/entrypoint.sh:8`), exits 1 on an empty `ETH_RPC_URL`/`CLICKHOUSE_HOST` (`:25-33`), turns an invalid, unset or non-lowercase `MODE` into `minimal` with only a WARNING line in the log (`:36-39` is case-sensitive, so `MODE=Custom` loses its `DATASETS` even though `src/config.py:45-50` would have lowercased it), probes ClickHouse with `curl -s` and no `--fail` (`:50-53`), so wrong credentials or an HTTP 5xx pass the probe (only a transport failure aborts it, under `set -e` (`:2`) with curl's own exit code; the `exit 2` branch at `:55-60` is unreachable), and then runs `exec python -m src` (`:69`). An invalid `OPERATION` crashes at start (`src/config.py:42`) and is not defaulted; `DATASETS` is honoured only under `MODE=custom`, and `custom` with an empty `DATASETS` silently becomes blocks/transactions/logs (`src/config.py:88-104`). Valid modes: `minimal` (blocks, transactions, logs), `extra` (contracts, native_transfers, traces), `diffs` (balance/code/nonce/storage diffs), `full` (all ten) and `custom` (`DATASETS`) (`src/config.py:16-22,93-102`). Per batch and per dataset, the indexer runs one `cryo <dataset> --blocks a:b --output-dir /app/data/worker_<id> --rpc $ETH_RPC_URL --overwrite --requests-per-second N --max-concurrent-requests N --columns … --network-name <chain>` (indexer `src/worker.py:35,277,403-425`).

Sources: Gnosis cryo-indexer stack `locals.tf:87-154,206`, `cronjob.tf:19,25`; Celo cryo-indexer stack `locals.tf:63-105,148`, `cronjob.tf:22,28`. Per-workload env, lookbacks, probes and resources belong to the indexer's own `AGENTS.md` and the stacks' `locals.tf`; the running image tag is the `image =` line there. Single writer: one Deployment per database at `replicas = 1` with strategy `Recreate` (Gnosis `deployments.tf:40,46-48` + `locals.tf:53`, Celo `deployment.tf:23,29-31` + `locals.tf:37`). The target tables are `ReplacingMergeTree(insert_version)` on natural keys (indexer `migrations/002_create_blocks.sql:25-27`, `003:33-35`, `004:19-21`, `007:27-29`), so re-inserted rows collapse only at a background merge; until then every read without `FINAL` counts them twice. The stacks' comment beside `strategy` ("the target tables do not dedupe") contradicts the schema. The indexer's range claims in `indexing_state` are advisory: auto-maintain DELETEs a range before it claims it (indexer `src/indexer.py:563`, then `src/worker.py:266`), and a one-shot `maintain` selects every non-completed range, `processing` included, then DELETEs and re-extracts it with no claim at all (`src/indexer.py:611-640,791`; maintenance workers skip `claim_range`, `src/worker.py:40,255-273`). Deliberately not deployed: the indexer's `historical`, one-shot `maintain`, `validate` and `migrations` Jobs plus, on Gnosis, a live-database migrations Job (`deployments.tf:4-9`, Celo `deployment.tf:7-10`), and a Celo live twin (none exists). The former AWS/EKS twins no longer exist; that cluster was torn down. Nothing runs migrations: only `python -m src migrations` (indexer `src/__main__.py:8-10`) or `python -m src.db.migrations` (`src/db/migrations.py:37`; the compose `migrations` service, `docker-compose.yml:157`) migrates, and both need an entrypoint override, because the image entrypoint drops container args (`scripts/entrypoint.sh:69` has no `"$@"`; compare `Makefile:75-77`). No cluster workload does either (Gnosis `locals.tf:43-44`). A patch that changes a table's shape needs a hand-run one-shot migration before the indexer re-pins its base.
Restart resumes from the **minimum** across datasets of `max(end_block) WHERE status='completed'`, aligned up to a batch boundary (indexer `src/indexer.py:119-130`, `src/core/state_manager.py:199-201`). If that checkpoint query fails at start it returns 0 (`src/core/state_manager.py:203-205`), so Gnosis (`START_BLOCK=0`) re-walks from genesis: completed ranges are skipped (`src/worker.py:257-263`), but at one status query per dataset per 100 blocks the writer is effectively wedged; Celo re-walks from its `START_BLOCK` floor instead. Every INSERT carries a fresh `insert_deduplication_token` (`src/db/clickhouse_manager.py:176,289`: main table and withdrawals), so a re-extracted batch is never rejected as a duplicate — which is why one replica and `Recreate` matter. Runbook section "Safe stop and restart".

## What does not exist, or does not do what its name says

- No scheduled build. `README.md:7,85` promise weekly / "every Sunday at 2 AM UTC" builds; the workflow has only `push: main` and `workflow_dispatch` (`.github/workflows/build-base.yml:3-13`). The public docs page contradicts itself: its Purpose paragraph still says "built weekly (or on-demand)", its Build Schedule section says "manual dispatch only" (omitting the push trigger), and its update steps say "push to main branch or trigger a manual build" (cerebro-docs `docs/data-pipeline/ingestion/cryo-base.md:7,80,96`). The workflow file wins over all of them.
- No `ENTRYPOINT`, `CMD`, `USER` or `WORKDIR` in the image (`Dockerfile:53-83` declares none). `docker run cryo-base` with no command gives the Debian base's default shell, not `cryo`; the binary runs as root; `README.md:21`'s `WORKDIR /app` is the consumer's line, not this image's.
- No check of the consumer's runtime contract. The indexer depends on this image's `python` symlink (`Dockerfile:67-68`; indexer `scripts/entrypoint.sh:69`), bullseye's python3 + pip (`Dockerfile:53,60-61`; indexer `Dockerfile:16-17`) and gcc/g++ for wheels (`Dockerfile:58-59`). Changing any of them breaks the indexer's next build, not this one.
- "Test Cryo installation" cannot fail: `Dockerfile:75-78` closes the `&&` chain with `|| true`, which swallows a failing `cryo --version` as well as the column grep. A green build is not evidence the binary runs.
- `01_null_traces.py` reports success on a half-applied patch: each of its two regexes only warns when it finds no match, and `main()` returns `True` if either matched (`patches/01_null_traces.py:66-71,96-101,103-105`). A cryo bump that moves one function ships with one trace path unpatched. Its idempotency marker (`:29-31`) is written by either replacement (`:53,83`), so after a half-apply a local re-run reports `skipped` and never patches the second function.
- `apply_patches.py` run from this repo's root fails every patch: `TARGET_FILE`s are relative to cwd (`patches/01_null_traces.py:18`, `patches/02_withdrawals.py:13`), so outside a cryo checkout both print `not found`, return `False`, and the runner exits 1 (`apply_patches.py:95-97`). It works in Docker because `Dockerfile:35` runs it with the cryo checkout as cwd (and `:36` puts `patches/` beside the script); from a cryo checkout, `python3 <cryo-base>/apply_patches.py` works too.
- An empty `patches/` directory builds an **unpatched** cryo and exits 0 (`apply_patches.py:38-40`); a *missing* `patches/` directory — looked up beside the script, not in cwd — is exit 1 and stops the build (`apply_patches.py:28-29,31-33`); a patch file without `main()` is skipped, not failed (`apply_patches.py:65-68`). The indexer always passes `--columns … withdrawals` for blocks (indexer `src/worker.py:76-77,414-418`), and a failed blocks batch fails every dataset in the range (`src/worker.py:151,154-157`), so an unpatched base is expected to fail every range: each is retried `MAX_RETRIES` times (default 3, indexer `src/config.py:59`) and then abandoned (`blocks` marked `failed`, the other datasets left with no row) while the loop moves on (`src/indexer.py:172-196,219-239`). The writer keeps pace with the head but completes nothing: `highest_completed` freezes, and auto-maintain's retries inside its window fail the same way. That stock cryo rejects the unknown column is unverified here (and see the empty-output hazard below): prove it with a one-block run before re-pinning.
- `patches/_template.py.example:56` ends with a stray Markdown fence. Copied verbatim to `NN_name.py` it is a `SyntaxError`, which the runner catches as a failure and the build stops (`apply_patches.py:83-85`).
- Every `workflow_dispatch` build that keeps a non-empty `cryo_commit` drops the `-patched` suffix from the `cryo.commit` label, even one left at its default: the input's non-empty default satisfies the `!= ''` guard (`.github/workflows/build-base.yml:12,39`), so both `sed`s run and rewrite the label (`build-base.yml:42` vs `Dockerfile:83`) although patches still ran. Only push-to-main builds, and dispatches with the input cleared, carry the suffix. A dispatch with a NEW commit additionally produces a `latest` that no commit in this repo describes (`build-base.yml:38-42` edits the Dockerfile in the runner only). The label suffix is not evidence of patching either way.
- `README.md:18` shows `FROM ghcr.io/gnosischain/cryo-base:latest`; the real consumer pins a date tag (indexer `Dockerfile:2`). Rebuilding `latest` changes nothing downstream until that line changes.
- No `.dockerignore`: `.gitignore:11` ignores the name, so a normal `git add` never picks one up (only a forced add would track it). A local `docker build` sends the whole tree, `.cryo/reports/` included, as context; only the selective COPY at `Dockerfile:22-23` keeps the reports out of the image, so never widen it to `COPY . .`.

## Hazards

- **A provider error becomes an empty range.** Patch 01 turns any trace error whose text contains `null` or `invalid type` into `[]` (`patches/01_null_traces.py:56-61,86-92`); the indexer records the range `completed` with `rows_indexed = 0`. auto-maintain does re-open zero-row `traces` ranges as `failed` (indexer `src/core/state_manager.py:495,535-549`, `src/indexer.py:475-484`), but only inside its lookback window (`AUTO_MAINTAIN_LOOKBACK_HOURS` × a hardcoded 720 blocks/h, `src/indexer.py:424-426,436`: 48 h on Gnosis, only ~9.6 h of Celo's ~1 s blocks, Celo `locals.tf:99`) and only usefully once the RPC recovers — a persistent fault re-completes at 0 rows every run, and anything older than the window is permanent. Condition: RPC instability on a traces range. Safe alternative: the runbook's gas-burned check on the suspect ranges, then re-open them as `failed` by hand — runbook sections "Gap" and "Corrupt range".
- **A cryo failure whose text contains `no data`, `empty`, `zero` or `0 items` becomes a completed 0-row range.** The indexer treats any non-zero cryo exit with one of those substrings (case-insensitive) in stderr/stdout as an empty dataset (indexer `src/worker.py:437-445`) and marks the range `completed` with 0 rows (`src/worker.py:322-330`). auto-maintain re-opens zero-row ranges only for blocks, transactions, logs and traces (`src/core/state_manager.py:495`) and only inside its window; a hole in contracts or native_transfers is permanent. Condition: any base bump whose error wording changes (a new patch, a new cryo commit, a rejected column). Safe alternative: in the one-block local run, force a failure (bad column, bad RPC) and read cryo's error text for those words before re-pinning.
- **Any new base tag can change column output, and that flows into every table the indexer writes** once the indexer re-pins its base. A rebuild of the same commit is not guaranteed to be the same binary: rustup installs whatever stable is current unless the cryo checkout pins a toolchain (`Dockerfile:18`), the Debian base and apt packages are unpinned (`:4,7-15,53,55-65`), and `cargo build` runs without `--locked` (`:48`), so dependency resolution is only as pinned as cryo's own `Cargo.lock` at that commit (unverified here). Condition: any edit under `patches/`, any change to `Dockerfile:30`, or a plain rebuild, including the one every push to `main` triggers. Safe alternative: build locally; run the indexer's `scripts/check_columns.py <rpc>` against the new binary (it diffs cryo's dry-run column list against a hand-kept copy of the migration columns, `scripts/check_columns.py:8-12,81-130,150-187`; its blocks list has no `withdrawals`, and it prints the RPC URL at `:165`, so use your own endpoint), plus `cryo help blocks` and a one-block extraction with `--columns … withdrawals`; then diff the parquet schema against the currently pinned date tag before touching the indexer's `FROM`.

## Health and verification is a warehouse query

This repo has no liveness signal of its own; the image is healthy when the indexer embedding it is writing:

```sql
SELECT dataset, max(end_block) AS highest_completed, max(created_at) AS last_write
FROM execution.indexing_state WHERE status = 'completed' GROUP BY dataset ORDER BY dataset;
```

Healthy: `last_write` within a couple of batch intervals for every dataset — the loop writes only when a full `BATCH_SIZE` of confirmed blocks exists (indexer `src/indexer.py:160-163,240-242`), so a caught-up `execution` writer lands a 100-block batch about every 8 min (5 s blocks), `execution_live` its 10-block batch every ~1 min, `celo_execution` its 100-block batch every ~2 min (~1 s blocks) — and `highest_completed` must advance between two reads: an auto-maintain run refreshes `last_write` on old ranges without moving the head (`created_at` defaults to `now()`, indexer `migrations/012:11`; `src/core/state_manager.py:127-132`; `src/indexer.py:494-497,544-565`, because both crons run `WORKERS=8`, Gnosis `locals.tf:153`, Celo `locals.tf:104`; the `WORKERS=1` path is `:523-528`). `POLL_INTERVAL` (60 s / 5 s / 15 s) is how often the loop re-checks the head, not how often it writes; `highest_completed` trails head by about `CONFIRMATION_BLOCKS`. Repeat for `execution_live` and `celo_execution`. Morning-check equivalent: `dateDiff('minute', max(block_timestamp), now())` on `<db>.blocks` is healthy at about 66 min on `execution` (`CONFIRMATION_BLOCKS=720` at 5 s) and about 1 min on `execution_live` (private runbook `00-morning-check.md:37-38,47-48`); the morning check has no Celo row.
Coverage is per-dataset batch presence in `indexing_state`, never `count()` on `blocks`: the runbook's "Gap" section holds the expected-vs-present query and the gas-burned check. A range's current status is `argMax(status, (created_at, insert_version))` grouped by `dataset, start_block, end_block`: `FINAL` does not collapse a range whose rows fall in two months, because `indexing_state` is `ReplacingMergeTree(insert_version)` partitioned by `toYYYYMM(created_at)` (indexer `migrations/012_create_indexing_state.sql:20-22`). Is the deployed binary the patched one? Rows in `execution.withdrawals` for recent blocks are the warehouse-visible proof of patch 02 — the indexer fills that table only from the patched column (indexer `src/db/clickhouse_manager.py:160-191,204`).
Not a health signal: a green base-image build, `cryo --version` passing, pod Running, exit 0, a uniform ~80 s auto-maintain run (`Auto-maintain: no issues found in recent data`, indexer `src/indexer.py:487`, meaning "nothing in window"), `No real gaps found` (`src/core/state_manager.py:348`; a hole under 100 blocks, such as a single missing 10-block `execution_live` batch, is dropped at `:326`), row counts on `blocks`, Prometheus counters, or a quiet chain-lag alert during an RPC outage.

## Rules for agents

- Derive from code: `Dockerfile`, `apply_patches.py`, `patches/`, `.github/workflows/build-base.yml`. The README is the least trusted source in this repo (see above); the runbook is second; this file's numbers are third. Local tooling is not production: `docker build` / `docker run` here prove that a binary builds, not that the indexer works with it.
- Never run a writer against the production warehouse from a laptop. `cryo` itself cannot, but the indexer wrapping it can: `OPERATION` defaults to `continuous` and `MODE` to `minimal` (indexer `src/config.py:42,45`), and the entrypoint refuses to start only on an empty `ETH_RPC_URL`/`CLICKHOUSE_HOST` (`scripts/entrypoint.sh:25-33`) or a ClickHouse transport failure (`:50-53`). Every indexer make target that starts a container (`continuous`/`start`, `minimal`/`extra`/`diffs`/`full`/`custom`, `historical`, `test-range`, `maintain`, `auto-maintain`, `validate`/`status`, `live`, `shell`, `run-migrations`, `run-migrations-live`; `Makefile:64-183`) and every compose service (`docker-compose.yml:60-218`) reads `CLICKHOUSE_DATABASE` and credentials from the indexer's `.env` (`Makefile:5-8`; default `blockchain`, `docker-compose.yml:11`, `src/config.py:37`). `make live` defaults to `execution_live` (`docker-compose.yml:140`) and `run-migrations-live` hardcodes it (`Makefile:72`). With production credentials in that `.env`, any of them reaches production, every one but `validate`/`status` writes rows, and even a bare run creates its database there (`src/db/clickhouse_manager.py:36,55`). `make shell` (`Makefile:146-147`) is not a shell: the entrypoint ignores container args (`scripts/entrypoint.sh:69`), so it starts a continuous `MODE=custom` writer (`docker-compose.yml:116-124`); `make test-range` (`Makefile:181-183`) is a historical write of blocks 18000000-18001000. To inspect the image, use `docker run --rm -it --entrypoint bash cryo-indexer:latest` (the local tag, `Makefile:62`). Never "test the new base" by giving a local indexer the production ClickHouse secret.
- Never assume access to the cluster or the private deployments repository. Propose exact commands for a human to run. Never run a git write, a Terraform apply, a cluster-mutating command or an image push yourself; read-only plans and read-only cluster reads are fine where you already have access.
- Never a second writer, never more than one replica, never `RollingUpdate` — that is the indexer stacks' rule and it does not change because the base image did.
- Never change the pinned cryo commit via `workflow_dispatch` alone. Change `Dockerfile:30`, `Dockerfile:83` and the dispatch default at `.github/workflows/build-base.yml:12` in one commit (`README.md:9` too); otherwise a dispatch left at its default rebuilds the old commit and publishes it as `latest` and today's date tag (`build-base.yml:39-42,50-52`).
- A new base reaches production only in three human-gated hops: (1) a cryo-indexer PR changing its `Dockerfile:2` date tag, (2) that indexer image built by the indexer's CI on merge to `main` (indexer `.github/workflows/build-and-release.yml:3-6`), (3) the deployments stacks' `image =` repinned by a human (see "Deployments stacks" below). Prove the base before hop 1 on a Gnosis block after the withdrawals fork (the README's example block, `README.md:30`, is one) with both the `blocks` and `traces` datasets, and compare the parquet schema with the currently pinned date tag.
- A new patch must return `False` when any anchor is missing (copy `02_withdrawals.py`'s error list, not `01`'s warn-and-continue), keep an idempotency marker, name a real `TARGET_FILE` under the cryo checkout, and ship with a one-block `docker run` proving the column or behaviour exists.
- A local `cryo` run writes its full command line, RPC key included, into `<output>/.cryo/reports/*.json` (ignored here by `.gitignore:8`, nowhere else) and spends that endpoint's rate limit: use your own endpoint, never un-ignore `.cryo/`, and never paste a report into an issue, PR or chat.
- As of 2026-09-23 the maintainer's checkout already holds two 2025-07-22 reports under `.cryo/reports/` whose `cli_command` carries a third-party RPC URL with an `apiKey` query parameter. They are untracked (`.gitignore:8`). Do not open, quote or copy them; ask the human to delete them and rotate that key if it is still live.
